# 匿名评审分配系统（Review Assignment · MCMF）

基于 **Python + FastAPI + SQLite + 原生 HTML/CSS/JS** 的单容器 Web 应用。
用**最小费用最大流（Min-Cost Max-Flow）**为稿件分配评审人：

- ✅ **冲突边绝不使用**——作者冲突的“稿件–评审人”边根本不会加入流网络；
- ⭐ **主审资格硬约束**——评审人可标记“可任主审”，稿件可设需主审人数（0~2 且不超过所需评审数）；主审同样占用稿件需求、个人容量与机构名额，同一人对同一稿件至多分配一次；主审不足时仍返回最大可行分配，并分别报告主审缺口与总人数缺口；
- ⚖️ 费用同时惩罚 **主题不匹配**（β × 未覆盖主题数）与 **评审负载偏差**（凸增边际成本 α·k，天然均衡）；
- 🔒 允许**锁定少量既有分配后重新求解**，锁定边预占稿件名额、评审容量与**机构名额**并参与负载计费；合资格的有效锁定按评审人 ID 顺序优先抵扣主审名额；
- 🏛️ **机构多样性硬约束**：评审人可填写可选机构，可配置“每篇稿件同机构最多人数”（0 为关闭）；未填写机构者不计入该上限；历史锁定已超限时保留锁定、发出警告且不再向该稿该机构分配新人，新增锁定会超限时接口返回 **409**；
- 📨 **利益冲突自助申报（一次性链接）**：管理员可为每位评审人生成一次性申报链接，链接绑定**签发时的稿件清单版本**，评审人打开后**只能看到稿件标题**并勾选冲突；提交在**单个事务**中合并进冲突矩阵并立即失效，重复提交、稿件增删或标题变化后提交均返回 **409 且不做任何部分写入**，管理员重新生成链接即可恢复；
- 🧪 **方案沙盒（临时参数预览）**：在“求解参数与默认值”区域输入**临时**的主题不匹配权重、负载权重与机构上限即可生成预览——纯内存重算，**不改动** settings、assignments、锁定项或 last_solution；预览展示与当前方案相比的**新增/移除评审配对、总成本、未满足人数与主审缺口变化**，并绑定稿件、评审人、冲突、锁定与参数的**版本指纹**；「采用」仅在指纹仍一致时于**单个事务**内写入临时参数与预览分配，否则返回 **409** 提示重新预览，杜绝过期结果覆盖并发修改；
- ⛔ 容量或主审不足时给出**未满足稿件清单**和**可复核的原因明细**（主审资格、冲突排除人数、**机构上限排除人数**、各候选评审剩余容量与主题覆盖情况、全局容量缺口）；
- 🗃️ SQLite 单文件持久化，数据卷挂载；无前端构建步骤、无第三方 JS 依赖。

## 一条命令启动

需要安装 Docker（含 Compose 插件）。在项目根目录执行：

```bash
docker compose up --build -d
```

这一条命令会完成：

1. 构建镜像并安装全部 Python 依赖（`requirements.txt`）；
2. 启动容器时**自动初始化数据库**：建表、写入默认求解参数、载入演示数据（首次启动）；
3. 在后台启动 FastAPI / uvicorn 服务。

启动后访问：

> **http://localhost:8000**

- 前端页面：<http://localhost:8000/>
- 接口总览（Swagger）：<http://localhost:8000/docs>
- 健康/状态接口：<http://localhost:8000/api/state>

停止 / 查看日志：

```bash
docker compose logs -f
docker compose down          # 停止（数据保留在卷 review-data 中）
```

不想要演示数据（空库启动）时，将 `docker-compose.yml` 中的 `SEED_DEMO` 改为 `"0"` 后重建；
或删除卷重新开始：`docker compose down -v`。

### 不使用 Docker（本地开发）

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
python -m uvicorn app.main:app --host 0.0.0.0 --port 8000
```

数据库默认创建在 `./data/review.db`（可用环境变量 `DB_PATH` 覆盖），首次启动自动建库并写入演示数据。

冒烟测试（仅标准库）：

```bash
python -m tests.test_smoke            # 求解器与既有功能
python -m tests.test_declarations     # 利益冲突自助申报（一次性提交/409/清单版本/哈希不回传/迁移）
python -m tests.test_sandbox          # 方案沙盒（预览不落库/版本指纹/单事务采用/409 过期保护）
```

## 使用说明

页面共 4 个标签页：

| 标签页 | 功能 |
| --- | --- |
| **分配结果** | 一键“重新求解分配”；查看每篇稿件的评审人（⭐ 标识实际主审）、**机构构成**、费用拆解、评审人负载条；🔒 锁定/解锁既有分配；展开未满足稿件的原因明细（主审缺口与人数缺口分别列出）；调整求解权重、机构上限与默认值；**方案沙盒**：用临时参数生成预览并与当前方案对比，确认后采用 |
| **稿件** | 录入稿件主题（逗号/顿号分隔）、设置**每稿所需评审数**与**需主审人数**（0~2，不超过所需评审数）；编辑、删除 |
| **评审人** | 录入评审人擅长主题、**可选所属机构**、**个人容量**与**是否可任主审**；编辑、删除 |
| **作者冲突** | 用勾选矩阵登记“稿件–评审人”冲突；已锁定的分配需先解锁才能登记冲突 |
| **利益冲突申报** | 为评审人生成/重新生成/撤销**一次性自助申报链接**；按评审人展示**未签发、待提交、已提交、已失效**状态与「清单已变化」提示 |

顶部按钮：

- **▶ 重新求解分配**：按当前数据与权重运行 MCMF，生成完整分配；
- **载入演示数据**：恢复内置示例（含一个刻意制造的容量不足样例）；
- **清空全部**：删除所有稿件、评审人、冲突与分配。

> 锁定任意分配后系统会**立即自动重新求解**；无需再点“重新求解”。

## 利益冲突自助申报（一次性链接）

适用于管理员不方便代填冲突矩阵、需要由评审人本人确认回避关系的场景。

### 操作流程

1. **管理员签发**：在「利益冲突申报」页为评审人点击「生成申报链接」。
   链接形如 `http://<站点>/declarations/<一次性令牌>`，请立即复制并发送给评审人
   （明文链接仅在生成时展示这一次，系统此后不再保存/展示明文）。
   每位评审人至多有一个**待提交**链接：重新生成会使旧链接立即失效（状态记为「已失效 · 重新签发顶替」）。
2. **评审人勾选**：评审人打开链接，页面**仅列出签发时稿件清单中的标题**（不含主题等其他信息），
   勾选自己存在利益冲突、不应评审的稿件后提交。未勾选不会移除此前已登记的冲突。
3. **一次性合并**：提交在**单个数据库事务**内完成“版本校验 → 并入冲突矩阵（union）→ 链接立即失效”。
   - 重复提交（含双击/并发）返回 **409**，已合并的冲突不会重复写入；
   - 勾选稿件若存在**锁定的既有分配**，整单返回 **409**（提示先解锁），**不做部分写入**，解锁后可用原链接重试；
   - 提交包含清单外稿件 ID 返回 **400**，同样不写入。
4. **清单版本保护**：链接绑定签发瞬间的稿件清单版本（全部稿件 ID + 标题的哈希）。
   签发后若稿件有**新增、删除或标题变化**，评审人页面会提示「清单已变化」，
   提交返回 **409 且不写入**；管理端该评审人的待提交状态标记**「待提交 · 清单已变化」**，
   管理员点击「重新生成链接」即可让评审人按最新清单申报。
5. **撤销**：管理员可随时撤销**待提交**链接（评审人将无法打开/提交）；
   已提交、已失效的链接不可撤销（返回 409）。

### 管理端状态

按评审人展示其最新一条申报记录的状态：

| 状态 | 含义 |
| --- | --- |
| **未签发** | 从未生成过申报链接 |
| **待提交** | 链接有效、等待评审人提交；附带「清单已变化」提示时需重新生成 |
| **已提交** | 评审人已提交，勾选冲突已合并进冲突矩阵，链接已失效（显示提交时间与勾选数） |
| **已失效** | 被管理员撤销，或因重新生成新链接而被顶替 |

### 安全设计

- 令牌由 `secrets.token_urlsafe(32)` 生成；数据库**只保存其 SHA-256 哈希**（`conflict_declarations.token_hash`），
  任何 API 响应（`/api/state`、管理端申报列表、错误消息）与应用日志**均不回传哈希**；
  明文令牌只在签发响应中出现一次。
- 评审端接口为公开接口（持令牌即可访问），但只返回稿件**标题**，不暴露评审人名单、
  机构、主题、冲突矩阵等其他数据。
- 提交为幂等合并（`INSERT OR IGNORE`），配合 `BEGIN IMMEDIATE` 串行化，
  保证“绝不部分写入”；连接设置了 `busy_timeout` 以处理并发点击。

> 提示：一次性令牌会出现在反向代理/uvicorn 的常规访问日志 URL 中（这是凭链接访问机制所固有的）；
> 库内与业务响应中始终只有哈希。如需更严格控制，可在反向代理层对 `/declarations/` 路径脱敏。

## 方案沙盒（临时参数预览）

适用于“想看看调参效果，但不想直接改动正式设置与分配”的场景。入口在「分配结果」页
**「求解参数与默认值」** 区域内，与既有一键求解流程互不干扰。

### 操作流程

1. **输入临时参数**：填写临时的主题不匹配权重 β、负载偏差权重 α 与每篇同机构上限 γ
   （默认带入当前设置值，改动任意一项即可）。
2. **生成预览**：`POST /api/sandbox/preview` 用临时参数在**内存中**重跑同一套两阶段 MCMF，
   **不写入** settings、assignments、锁定项或 last_solution。预览返回：
   - **配对差异**：与当前分配相比的**新增 / 移除评审配对**清单（含稿件、评审人、是否主审）；
   - **指标对比**：总成本、已满足评审数、**未满足人数**、**主审缺口**的当前值 / 预览值 / 变化量；
   - 预览下的未满足稿件简表与求解警告；
   - **版本指纹**：对稿件、评审人、冲突、锁定分配与求解参数（settings 三项）取规范化
     JSON 的 SHA-256，随预览一并返回（非锁定的自由分配是上述数据的确定性求解结果，
     不参与指纹，因此“用相同数据重新求解”不会使预览失效）。
3. **采用方案**：`POST /api/sandbox/adopt` 携带临时参数与指纹。服务端在
   **单个事务（`BEGIN IMMEDIATE`）**内先复核指纹：
   - **一致** → 求解是确定性的，重算结果与预览完全相同；同事务写入三项临时参数、
     以预览分配替换全部非锁定分配（锁定保留）并更新 last_solution；
   - **不一致**（预览期间稿件/评审人/冲突/锁定/参数被并发修改）→ 返回 **409**，
     **不写入任何内容**，前端提示重新生成预览，杜绝过期结果覆盖并发修改。
4. **清除预览**：仅丢弃前端预览，不影响任何数据。

> 沙盒预览与正式求解共用同一个求解内核（`solver.compute_solution`），
> 因此预览指标、配对与采用后的实际结果严格一致。

## 优化模型

### 网络结构

```
        cap = 缺口        cap = 1            cap = 1           凸增单位槽位
S ───────────────► M_i ───────────────► R_j ───────────────► T
  (稿件需求-锁定数)      (无机构：直接边)      (无冲突且未锁定)      cost = α·k, k=1..容量

                     cap = γ−锁定数          cap = 1
                 ┌────────────────► O_{i,a} ─────────┐
S ──────────► M_i ┤  (机构节点：每篇稿件×每个机构)      ├─► R_j(属于机构 a) ──► T
                 └────────────────► …（未填写机构走直接边）
```

- **S → 稿件**：容量 = 该稿件本轮尚缺的人数（需求 − 有效锁定数 − 上一阶段已分配数）；
- **稿件 → 评审人**：容量 1（同一评审对同一稿件至多评审一次）；
  **冲突边与已锁定/已分配边不会被创建**，因此从结构上保证绝不使用；
  费用 = `β ×（稿件主题 − 评审擅长主题）的数量`；
- **机构多样性（硬性）**：当 `institution_cap = γ > 0` 且评审人填有机构 a 时，
  分配边改走 **M_i → O_{i,a} → R_j**，其中机构节点入边容量 = `γ − 该稿来自 a 的已占用数`。
  锁定与主审先占机构名额；名额被占满（或历史锁定已超 γ）时机构节点不建立入边，
  从而本稿绝不会再被分到该机构的人。**未填写机构的评审人走直接边，不占用、也不受机构名额限制。**
- **评审人 → T**：容量拆为单位“负载槽位”，第 k 个槽位费用 `α·k`（k 从该评审已占用数之后连续计）。
  边际成本递增使流算法自动偏好更空闲的评审人——这就是“负载偏差”惩罚。

求解分两轮调用上述网络：第一轮仅含合资格候选、需求为各稿剩余主审名额（主审阶段）；
第二轮为其余全部候选、需求为剩余人数（普通阶段）。详见下节。

### 主审资格硬约束（两阶段求解）

- 评审人可勾选**“可任主审”**；稿件可设置**需主审人数** `required_leads`（`0~2`，且不得超过所需评审数；
  默认为 `0`，即该稿不启用主审约束）。只有合资格评审人才会被认定为主审（资格为硬约束）；
- 求解分两个阶段（同一套流网络模型）：
  1. **主审阶段**：仅对合资格候选建网，把各稿剩余主审名额作为需求求最大流。
     主审与普通人选走完全相同的稿件需求、个人容量槽位与机构名额，
     同一人对同一稿件至多分配一次；
  2. **普通阶段**：把主审分配视同锁定（预占需求/容量/机构名额），对其余候选求普通分配。
     主审阶段的流是全局网络中的可行流，在其残量网络上继续增广必达全局最大流，
     因此“主审优先”**不会减少最终的总分配人数**；
- **锁定抵扣**：合资格的有效锁定按**评审人 ID 升序**优先抵扣主审名额，不足部分由自由分配补齐；
  非合资格锁定永远不算主审；
- **主审不足时不阻塞**：仍返回最大可行分配，该稿列入未满足清单，
  分别给出 `lead_deficit`（主审缺口）与 `deficit`（总人数缺口），
  候选明细逐人标注主审资格、冲突、剩余容量与机构阻断；
- 求解结果中 `solution.lead_pairs` 列出全部**实际主审**（稿件, 评审人）对，
  结果页以 ⭐ 徽章标识；总览卡片显示“主审已认定 / 共需”。

### 机构多样性约束

- 评审人的机构为**可选**自由文本；空（未填写）表示独立、不计入任何机构上限；
- 设置 `institution_cap`（每篇稿件同机构最多人数）：`0` 为关闭，`≥1` 时与冲突、容量同级作为**硬约束**；
- 锁定先占用机构名额；若历史锁定本身已超过 γ（例如上限调小或导入存量数据）：
  **锁定强制保留**、求解警告逐条列出（`institution_lock_over_cap`），本次不再向该稿该机构安排新人；
- 通过接口新增一把锁会使该稿同机构人数超过 γ 时，`POST /api/assignments/lock` 返回 **409**，
  请先解锁一名该机构的锁定或放宽上限（把已有自由分配转为锁定不增加人数，故不拒绝）；
- 分配结果中每篇稿件返回 `solution.institutions`（机构、人数、其中锁定数、是否超限）。

### 锁定的既有分配

锁定边不进入网络，而是：

1. 预占该稿件一个名额（S→M 容量减 1）；合资格（可任主审）的锁定按评审人 ID 升序优先抵扣该稿主审名额；
2. 预占该评审一个容量槽位（自由槽位减少，锁定数超过容量时自由容量为 0，并给出告警）；
3. 预占一个**机构名额**（M→机构节点容量减 1；历史锁定超机构上限时见上）；
4. 按相同规则计入总费用（主题费 + 其所处槽位的负载费），保证锁定与新求解目标口径一致。

非法锁定（指向已删除对象、与冲突边重合、超过稿件需求）会被跳过并在“求解警告”中逐条列出，**不会静默处理**。

### 容量或主审不足时的输出

最大流流量小于总需求、或某稿主审人数不足时，对每篇未满足稿件返回：

- `required / assigned / deficit`（总人数缺口）与 `lead_required / lead_assigned / lead_deficit`（主审缺口）；
- 自然语言原因（主审候选池的阻断分解、冲突排除人数、**机构上限排除人数**、候选剩余总容量、是否全局容量不足等）；
- `details.candidates`：每位**非冲突且未已分配**评审人的主审资格（`can_lead`）、剩余容量、未覆盖主题数，
  以及 `blocked_by_institution`（是否被机构上限硬性排除），可人工逐项复核。

### 可调参数（页面“求解参数与默认值”）

| 参数 | 默认 | 含义 |
| --- | --- | --- |
| `mismatch_weight` (β) | 10 | 每个未覆盖稿件主题的费用 |
| `load_weight` (α) | 2 | 第 k 个负载槽位费用系数（越大负载越均衡；设 0 关闭负载惩罚） |
| `institution_cap` (γ) | 0（演示数据为 2） | 每篇稿件同机构最多人数；**0 关闭机构多样性约束**，未填机构者不计入 |
| `default_required_reviews` | 3 | 新建稿件的默认所需评审数 |
| `default_capacity` | 3 | 新建评审人的默认个人容量 |

> 想先“试算”再决定是否采用？用同区域的**方案沙盒**：输入临时 β/α/γ 生成预览，
> 对比新增/移除配对与成本、未满足人数、主审缺口变化后，再一键采用（指纹校验 + 单事务写入）。

MCMF 实现见 `app/mcmf.py`（SPFA + Successive Shortest Path，可正确处理残量网络中的负权反向边），
业务建模见 `app/solver.py`。

## REST API 摘要

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/state` | 一次性拉取全部数据（稿件/评审人/冲突/分配/申报链接状态/上次解；**不含令牌哈希**） |
| POST / PATCH / DELETE | `/api/manuscripts[/{id}]` | 稿件增改删（含 `required_leads` 需主审人数 0~2；超过所需评审数返回 400） |
| POST / PATCH / DELETE | `/api/reviewers[/{id}]` | 评审人增改删（含可选 `institution` 与 `can_lead` 主审资格） |
| POST / DELETE | `/api/conflicts`、`/api/conflicts/{m_id}/{r_id}` | 冲突登记/移除 |
| POST | `/api/reviewers/{id}/declarations` | 为评审人签发一次性申报链接；旧待提交链接立即失效；明文令牌仅本次返回 |
| POST | `/api/declarations/{id}/revoke` | 撤销待提交链接；已提交/已失效返回 **409** |
| GET | `/api/public/declarations/{token}` | 评审人查看：待提交时仅返回签发清单中的稿件标题；清单变化时 `stale=true` |
| POST | `/api/public/declarations/{token}/submit` | 一次性提交（`{"conflict_manuscript_ids":[...]}`）：单事务合并冲突并失效链接；重复提交/清单变化/锁定冲突返回 **409**，清单外 ID 返回 **400**，均不部分写入 |
| GET | `/declarations/{token}` | 评审人自助申报页面（静态页） |
| PUT | `/api/settings` | 权重、`institution_cap` 与默认值 |
| POST | `/api/solve` | 运行两阶段 MCMF 求解（先主审、后普通评审） |
| POST | `/api/sandbox/preview` | 方案沙盒：用临时 β/α/γ 内存重算并返回与当前方案的差异（新增/移除配对、总成本、未满足人数、主审缺口）与版本指纹；**不写入任何数据** |
| POST | `/api/sandbox/adopt` | 采用沙盒方案：指纹一致时在**单个事务**内写入临时参数与预览分配；指纹过期返回 **409** 且不写入，需重新预览 |
| POST | `/api/assignments/lock` | 锁定/解锁并立即重新求解；**新增锁定会使同机构人数超过上限时返回 409** |
| POST | `/api/demo`、`/api/reset` | 载入演示数据 / 清空（申报链接一并清空） |

所有写接口均返回最新的完整状态，前端无需二次拉取。

## 数据持久化与版本迁移

- Docker：SQLite 文件位于容器内 `/data/review.db`，映射到命名卷 `review-data`；
- 本地：默认 `./data/review.db`（已加入 `.gitignore`）。
- **保留既有数据**：应用启动时执行幂等迁移，旧版本数据库会自动
  `ALTER TABLE reviewers ADD COLUMN institution TEXT NOT NULL DEFAULT ''`、
  `ALTER TABLE reviewers ADD COLUMN can_lead INTEGER NOT NULL DEFAULT 0`、
  `ALTER TABLE manuscripts ADD COLUMN required_leads INTEGER NOT NULL DEFAULT 0`，
  并幂等创建 **`conflict_declarations`（利益冲突自助申报链接表，含令牌 SHA-256 哈希、
  签发稿件清单快照与版本哈希、状态及“每位评审人至多一个待提交链接”的部分唯一索引）**，
  并补入新设置项 `institution_cap = 0`（默认关闭，升级后行为与旧版本一致）；
  主审约束对旧库同样**默认关闭**（所有评审人不可任主审、所有稿件需主审 0 人），
  在表单中逐稿/逐人开启即可；`docker compose up --build` 升级无需手动操作，卷中历史数据、锁定均保留。
